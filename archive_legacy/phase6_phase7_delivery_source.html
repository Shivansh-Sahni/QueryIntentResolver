1. Executive Summary

This revision upgrades the Phase 6/7 package from a good first baseline into a more defensible team handoff. The main changes are: normalized labels and routes, explicit entity definitions, dataset balance exports, model comparison instead of a single-model story, and revised evaluation outputs in outputs_revised.

Most important conclusion: the low original scores were not only a modeling problem. The original package had label-space mismatches such as exact_lookup vs direct_lookup, repeated noisy templates assigned to conflicting persona labels, and shortcut rules that were too broad. After canonicalizing those issues and comparing stronger offline models, the revised package reaches 1.00 intent accuracy and 1.00 route accuracy on the normalized evaluation set. Persona accuracy improves to 0.73, but it is still the weakest signal, so query-only persona prediction should remain a supporting feature rather than the primary routing gate.
  • Original packaged baseline metrics from outputs/metrics.json: persona accuracy 0.48, intent accuracy 0.37, route accuracy 0.37.
  • Selected revised benchmark in outputs_revised: persona accuracy 0.73, intent accuracy 1.00, route accuracy 1.00, tier accuracy 1.00.
  • Best offline persona model: TF-IDF + Multinomial Naive Bayes.
  • Best offline intent model: word + character TF-IDF + Logistic Regression.
  • Dense semantic comparison baseline (TF-IDF + truncated SVD + Logistic Regression) also reaches 1.00 route accuracy after normalization, which supports the project lead's suggestion to move beyond plain sparse bag-of-words baselines.
  • Important caveat: these top-line scores are for the cleaned, route-aligned benchmark exported in outputs_revised, not the raw mislabeled artifacts.

3. Revised Phase 6 Classifier Design

3.1 Input and Output Contract

Input: raw query text, plus optional session/account metadata when available.

Primary output: intent_label, route, tier, intent_confidence, and extracted entity types.

Secondary output: persona and persona_confidence. Persona is still useful for analytics, personalization, and prompt framing, but the revised evaluation suggests it should not dominate routing when only the raw query text is available.

3.2 Recommended Runtime Architecture

  1. Normalize whitespace and casing for features while preserving the original text for logs.
  2. Apply a strict deterministic rule layer for only the safest cases: obvious B2B requests, school-only lookups, and very short single-school attribute queries.
  3. Run two models in parallel:
    • Persona model: TF-IDF + Multinomial Naive Bayes
    • Intent model: word + character TF-IDF + Logistic Regression
  4. Map intent to route and tier deterministically.
  5. If intent confidence is below threshold, or the predicted class is complex and underspecified, escalate to rewrite or LLM fallback.
  6. Log query, predicted persona/intent, confidence, entity types, chosen route, and whether a strict shortcut fired.

3.3 Why this model choice is better

Variant Persona accuracy Intent accuracy Route accuracy Interpretation
Original packaged outputs 0.48 0.37 0.37 Useful as a wiring proof, but distorted by label mismatch and broad shortcut rules.
Normalized Naive Bayes 0.73 1.00 1.00 Strong result after canonical cleanup. This is the simplest high-performing benchmark on the normalized set.
Dense semantic LSA + Logistic Regression 0.71 1.00 1.00 Useful offline proxy for the project lead's request to test a more semantic representation.
Selected mixed setup 0.73 1.00 1.00 Best combined offline setup. Character n-grams help with slang and typos; Naive Bayes still wins slightly on persona.

The revised recommendation is therefore:

  • Use Naive Bayes for persona until we have better persona-grounding metadata.
  • Use the character-aware Logistic Regression model for intent because it handles noisy student-style phrasing better than plain Naive Bayes.
  • Plan a future experiment with true pretrained sentence embeddings once that dependency can be added to the engineering environment.
  • Report the cleaned benchmark honestly as a normalization-sensitive result, not as proof that the raw original labels were already production ready.

3.4 Label Space Used in the Revised Package

The revised package uses a single canonical route-aligned label set:

direct_lookup, attribute_lookup, filtered_search, multi_constraint, comparison, recommendation, admissions_process, cost_financial_aid, campus_life_fit, career_outcomes, rewrite_needed, b2b_partnership.

Important fix: the old exact_lookup label is normalized into direct_lookup so the training data, evaluation data, route map, and reporting terminology are finally aligned.

4. Entity Schema

The revised package now defines the main entity types that matter for routing. The full artifact lives in entity_schema.csv.

Entity type Why it matters Typical extractor
school Direct page fetches, single-school facts, and seeded recommendations all depend on a known institution reference. Dictionary + fuzzy matching
major_or_program Needed to narrow filtered search, multi-constraint search, recommendation, and outcomes questions. Keyword lexicon + lightweight NER
location Used for geographic filters such as states, regions, or beach/warm-state preferences. Gazetteer + pattern rules
cost_constraint Separates finance guidance from simple metadata retrieval and supports affordability filtering. Regex + numeric pattern extraction
admissions_or_attribute_signal Captures acceptance rate, GPA, SAT, deadlines, housing, and similar school facts. Regex + keyword rules
fit_or_culture_cue Routes vibe/culture questions away from deterministic search into advisory or rewrite flows. Phrase list, optionally upgraded with LLM extraction later
career_outcome_cue Separates ROI, jobs, internships, and feeder-school questions from generic recommendations. Keyword patterns
b2b_request_type Supports safe short-circuiting into the B2B workflow. Strict regex rules
rewrite_cue Handles queries like "UCLA vibe but cheaper" that should be normalized before routing. Pattern rules

This suggests a practical release rule:

  • Below 0.60 intent confidence: still escalate or clarify, because low confidence is a better proxy for distribution shift than this cleaned benchmark shows.
  • 0.60 to 0.80: acceptable for offline routing on normalized data, but still a reasonable place for selective fallback in production.
  • Above 0.80: strong on the current benchmark, but continue logging and manually sampling outputs until a truly raw held-out set confirms the gain.

6.4 Recommended evaluation gate for the next iteration

  • Keep route accuracy as the main product metric, not just intent accuracy.
  • Treat persona as a secondary quality metric until user/session metadata can be added.
  • Add a second evaluation set that is intentionally left unnormalized so the team can measure raw-data robustness separately from canonicalized performance.
  • Track two explicit scorecards on each run: raw benchmark metrics and normalized benchmark metrics.

7. Team Recommendation and Next Steps

  1. Adopt the revised normalized label set and stop using exact_lookup as a separate label.
  2. Use the selected mixed baseline as the new offline benchmark: Naive Bayes for persona, character-aware Logistic Regression for intent.
  3. Keep easy short-circuiting extremely conservative. Today it should be limited to deterministic B2B and school-only lookup cases.
  4. Expand college B2B coverage because the dataset is still underrepresented there.
  5. Run a future experiment with real pretrained sentence embeddings after dependency setup is available; the strong LSA result is a good sign that denser semantic features are worth testing.
  6. If persona matters heavily to routing, use metadata from the session, profile, or page context rather than forcing the model to infer persona from very short queries alone.
